**Артефакт:** заметки с командами в Git

### Тест юнита 1

1. Что делает `chmod 4755 file` и зачем?
2. Hard link vs symlink? Что произойдёт с symlink при удалении оригинала?
3. Команда: показать все процессы с PID и памятью, отсортированные по памяти?
4. `df` vs `du` — разница, что использовать чтобы найти "куда делось место"?
5. Сервер не пускает по SSH после изменений. 5 шагов диагностики, по порядку.

### Мои ответы на тест юнита 1

1. Эта команда устанавливает SUID для того, чтобы другие пользователи могли запускать файл под правами владельца. Яркий пример: passwd.
2. Symlink ссылается на файл, а жесткая сслыка на его содержимое. При удалении оригинала, на который ссылается symlink, ссылка пропадет.
3. ps aux, но какие флаги сортируют по памяти не знаю. Так же мощной утилитой отображающей все процессы является - lsof, либо если спутится на уровень ниже можно мониторить содержимое каталога /proc
4. `df` показывает чем и как заняты разделы дисков и устройств, куда примонтировано, но эта команда отображает не всю память, которая занята. Дело в том, что ядро системы Linux использует кэширование для быстрого реагирования и здесь уже может помочь команда `du`, она может показать всю память под медиа.
5. Шаг 1. Если осталась открытая сессия можно через нее диагностировать, либо через VNC-консоль. В любом случае с хоста пропинговать, протрассировать сервер, чтобы исключить вину провайдера и установить доступность сервера.
Шаг 2. Проверить доступность порта, на powershel есть очень удобная утилита Test-NetConnection ip-адрес -Port 22
Шаг 3. На открытой сессии или через VNC - консоль проверить слушает ли сервер 22 порт через команду ss -tlpn, либо ss -tulpn если хочется посмотреть и tcp и udp порты, либо ss -tulpn | grep 22
Шаг 4. Проверить службу ssh, через команду systemctl status ssh, а так же логи через команду tail -50 /var/log/ssh.log
Шаг 5. Проверить конфиг, испраавить и перезагрузить службу. nano /etc/ssh/sshd.config, systemctl restart ssh

<details><summary>Эталонные ответы</summary>

1. SUID-бит (4) + 755. Файл запускается с правами владельца, не запустившего. Пример: `passwd`.
2. Hard link = второе имя того же inode. Symlink = отдельный файл-указатель. При удалении оригинала symlink становится битым (dangling).
3. `ps aux --sort=-%mem | head` или `ps -eo pid,user,%mem,cmd --sort=-%mem | head`.
4. `df` — что говорит ядро (на уровне ФС). `du` — фактический размер файлов. Расхождение — когда удалённый файл держится открытым процессом. Поиск: `du -h --max-depth=1 / 2>/dev/null | sort -h`.
5. (1) Web-консоль провайдера; (2) `systemctl status sshd`; (3) `/etc/ssh/sshd_config`; (4) `ufw status` / `iptables -L`; (5) `journalctl -u sshd -n 50`.

</details>

**Теория (3ч):**
- [ ] iptables vs nftables vs ufw
- [ ] Базовый hardening Ubuntu

**Практика (4ч):**
- [ ] ufw: только SSH-порт, 80, 443
- [ ] fail2ban для SSH
- [ ] unattended-upgrades

**Артефакт:** чек-лист + конфиги fail2ban

### Тест юнита 5

1. Команда: какие IP сейчас забанены fail2ban?
2. ufw vs iptables vs nftables — что под капотом, что выбрать в 2026?
3. Что произойдёт, если включить ufw без `ufw allow 22`?
4. SSH bastion/jump host — зачем, схема.
5. 5 правил hardening Ubuntu по умолчанию.

<details><summary>Эталонные ответы</summary>

1. `fail2ban-client status sshd`. Или `iptables -L f2b-sshd -n`.
2. iptables — старый user-space к netfilter. nftables — новый, заменяет iptables, единый синтаксис v4/v6/ARP. ufw — обёртка (в новых Ubuntu использует nftables backend). 2026: ufw для простых случаев, nftables напрямую для сложных.
3. **Потеряешь SSH-доступ.** ufw по умолчанию блокирует все incoming. Порядок: `ufw allow 22` → `ufw enable`. Имей под рукой web-консоль.
4. Bastion — единственный сервер, доступный из интернета по SSH. Остальные — только из private. `ssh -J bastion target` или ProxyJump. Плюсы: единая точка аудита, MFA в одном месте.
5. (1) SSH key only; (2) non-root user with sudo; (3) ufw минимум портов; (4) fail2ban; (5) unattended-upgrades; (6) поменян SSH-порт; (7) отключены неиспользуемые сервисы; (8) /etc в git.

</details>

### Тест юнита 7

1. `git merge` vs `git rebase`? Когда что?
2. Случайный `git reset --hard`. Как восстановить?
3. Detached HEAD — что, чем опасно, как выйти?
4. 10 коммитов в feature, многие — фиксы опечаток. Как причесать перед merge?
5. `git pull` vs `git pull --rebase`. Что лучше в команде?

<details><summary>Эталонные ответы</summary>

1. Merge — merge-коммит, нелинейная история. Rebase — переписывает поверх, линейная. Rebase для feature до публикации, merge для интеграции. **Никогда не rebase ветки, на которые работают другие.**
2. `git reflog` → находишь SHA → `git reset --hard <SHA>`. Reflog хранится ~90 дней.
3. HEAD указывает на коммит, не на ветку. Опасно: коммиты не принадлежат ветке, могут быть собраны GC. Выход: `git switch -c new-branch`.
4. `git rebase -i HEAD~10` → `pick`/`squash`/`fixup`/`reword`/`drop`.
5. `pull` = fetch + merge (паразитные merge-коммиты при локальных изменениях). `pull --rebase` = fetch + rebase (линейно). В команде: `pull.rebase = true` глобально.

</details>

2. Write-Ahead Log — журнал транзакций до применения. Используется для crash recovery, репликации, **PITR** (восстановление на любой момент при наличии базового бэкапа + WAL).

4. (а) Ротация (`find /backups -mtime +7 -delete`); (б) инкрементальные (pgbackrest, barman); (в) S3 с lifecycle; (г) zstd-сжатие.

### Тест юнита 11

1. Что делает SPF, как проверяется получателем?
2. DKIM vs SPF — принципиальная разница, что вместе закрывают?
3. Cloudflare proxied (оранжевое облачко) — плюсы и минусы.
4. A-запись 1.2.3.4, в CF proxied. Что покажет `dig` и почему?
5. DMARC `p=quarantine` vs `p=reject` — когда что?

<details><summary>Эталонные ответы</summary>

1. SPF — TXT-запись с разрешёнными отправителями. Получатель смотрит Return-Path → SPF домена → проверяет IP в списке.
2. SPF — **откуда** (IP). DKIM — **что контент не изменён**, подписан приватным ключом домена (публичный в DNS). DKIM работает через relay. Вместе: имеет право отправлять + контент не подделан. DMARC объединяет.
3. Плюсы: DDoS, кэш, WAF, скрытие реального IP, free SSL до клиента. Минусы: CF видит весь HTTPS-трафик; не-HTTP порты ломаются (нужен Spectrum); rate limiting может быть избыточным.
4. Покажет **IP Cloudflare**. В proxied A-запись подменяется anycast-IP CF. Реальный IP виден только в DNS-only режиме или в админке.
5. `quarantine` — в спам. `reject` — отклонить полностью. Стратегия: `p=none` (мониторинг) → `p=quarantine pct=10` → постепенно → `p=reject`. Без мониторинга = потеря писем.

</details>
