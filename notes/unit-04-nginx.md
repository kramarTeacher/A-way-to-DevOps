## Ключевые выводы для дежурства

### Прямой прокси - это `когда клиент осознанно идёт через посредника. Посредник делает запросы от своего имени. Сервер видит IP прокси.`
### Обратный прокси - это `когда посредник стоит на стороне сервера. Клиент думает что общается напрямую с сервером, не подозревая что за ним стоит несколько реальных серверов. Именно так работает Cloudflare — все запросы к твоему сайту идут через них.`
### Туннелирование - это `когда пакет целиком упаковывается внутрь другого пакета. Как письмо в конверте в другом конверте. Протокол внутри скрыт от промежуточных узлов. Мои IPIP-туннели на MikroTik — именно это, без шифрования. Формально в индустрии термин "туннель" часто используется и для незашифрованного (GRE, IPIP), и для зашифрованного варианта — контекст решает.`
### VPN -  `это туннель плюс шифрование содержимого. Провайдер видит только зашифрованный поток и не знает что внутри. VLESS+REALITY который ты настраивал — VPN с маскировкой под обычный HTTPS-трафик.`
### На каком уровне работает прокси? `Прокси работает на прикладном уровне (L7). Он разбирает содержимое: видит URL, HTTP-заголовки, домены. Может что-то запретить, кэшировать, залогировать, подменить.`
### Каким протоколом можно зашифровать ipip, GRE туннели? `IPsec`
### Прямой прокси — зачем нужен? `Корпоративная фильтрация, логирование, кэширование, обход блокировок, экономия трафика`
### Обратный прокси — зачем нужен? `Балансировка нагрузки, SSL termination (сертификат стоит только на прокси, внутренние сервера работают без TLS (проще администрировать), защита от DDoS, скрытие внутренней архитектуры, кэширование статистики, WAF (фильтрация вредоносных запросов до того как они дойдут до приложения))`
### Туннелирование — зачем нужно? `Объединение сетей, прокидывание протоколов, резервирование маршрутов, обход ограничений маршрутизации`
### VPN — зачем нужен? `Безопасное удаленное подключение, приватность, обход блокировок, site-to-site`
### Установка nginx `apt install nginx -y`
### Зачем в nginx разделили `sites-available/` и `sites-enabled/`? - `Это конвенция Debian/Ubuntu, не самого nginx. sites-available/ — здесь лежат все конфиги, которые вообще есть, независимо от того, активны они или нет. Это как "библиотека" конфигураций. sites-enabled/ — здесь лежат только те, что реально подключены к nginx. Обычно это не копии файлов, а симлинки на файлы из sites-available`
### Что делает `nginx -t` и почему **всегда** запускать перед reload? - `это проверка синтаксиса конфигурации без применения изменений. Читает nginx.conf и все подключённые через include файлы (в том числе всё из sites-enabled/; Проверяет синтаксис: правильные скобки, точки с запятой, известные директивы, корректность значений; Проверяет базовую консистентность: например, что упомянутые в root пути и т.п. синтаксически валидны; Ничего не перезагружает и не трогает работающий процесс — это чисто "сухой прогон". Почему это критично перед reload: systemctl reload nginx посылает мастер-процессу сигнал SIGHUP. Мастер пытается перечитать конфиг и запустить новые worker-процессы с новой конфигурацией. Если конфиг битый: Nginx не убивает старые рабочие процессы, пока не будут готовы новые — поэтому сайт формально не "падает" мгновенно; Но новые worker'ы с битым конфигом просто не запустятся, и в логах будет ошибка; Проблема в том, что при следующем restart (не reload) или падении/перезапуске сервера по любой причине — nginx уже не поднимется вообще, потому что стартовый конфиг невалиден. То есть reload с битым конфигом может дать обманчивое ощущение "всё ок, сайт же работает", а на самом деле ты уже в состоянии "один случайный restart — и сервис не встанет". nginx -t перед reload — способ поймать эту проблему заранее, пока ты ещё помнишь, что именно менял, а не среди ночи, когда сервер перезагрузился сам и сайт лёг.`
### В чём разница `systemctl reload nginx` vs `systemctl restart nginx`? - `Reload — плавно перечитывает конфиг, соединения не рвутся. Restart — рвёт все.`
### В логах `/var/log/nginx/access.log` найди свой curl-запрос. Какой формат по умолчанию? - `combined log format`
### Где находится дефолтный конфиг nginx? - `/etc/nginx/nginx.conf`
### Под каким пользователем стартует мастер-процесс для nginx? - `root`
### Под каким пользователем работают worker-процессы? - `www-data, строчка в конфиге - user www-data;`
### Сколько воркеров запустит nginx? - `auto = nginx сам определяет по числу ядер CPU (nproc). строчка в конфиге - worker_processes auto;`
### Файл, куда мастер-процесс пишет свой PID? - `/run/nginx.pid, строчка в конфиге - pid /run/nginx.pid;`
### Где для nginx находится глобальный лог ошибок? - `/var/log/nginx/error.log, строчка в конфиге - error_log /var/log/nginx/error.log; Глобальный лог ошибок — сюда попадает всё, что не переопределено на уровне конкретного server block (у меня eakramar.ru.conf переопределяет его своим error_log).`
### include /etc/nginx/modules-enabled/*.conf; - для чего в конфиге nginx эти строки? - `Это загрузка динамических модулей nginx — механизм, похожий на sites-available/sites-enabled, но для расширения функциональности самого nginx, а не для виртуальных хостов. libnginx-mod-http-geoip — определение страны по IP; libnginx-mod-mail — тот самый почтовый прокси, который закомментирован внизу конфига; libnginx-mod-stream — проксирование на уровне TCP/UDP (L4), не HTTP; libnginx-mod-http-image-filter, -http-perl, и т.д.`
### Что такое events { } в nginx? `блок настройки движка обработки соединений`
### worker_connections 768; Для чего в конфиге nginx эта строка? - `Максимум одновременных соединений на один воркер (включая соединения к бэкендам, если nginx работает как прокси). Грубая формула ёмкости сервера: worker_processes × worker_connections. При auto на, скажем, 2 ядрах — это 1536 одновременных соединений всего. Для статики этого обычно с запасом хватает.`
### multi_accept on; Для чего в конфиге nginx эта строка? - `Если включить — воркер за раз принимает все ожидающие соединения из очереди, а не по одному за цикл event loop. На практике редко нужно, может даже перекашивать нагрузку между воркерами.`
### http { } - для чего в конфиге nginx эта строка? - `контекст, общий для всех виртуальных хостов`
### sendfile on; - для чего в конфиге nginx эта строка? - `Включает syscall sendfile() — файл отдаётся клиенту прямо из kernel space в сокет, минуя копирование через userspace-буфер nginx. Быстрее и меньше нагрузка на CPU при отдаче статики (как раз мой случай с eakramar.ru).`
### tcp_nopush on; - для чего в конфиге nginx эта строка? - `Работает в связке с sendfile. На Linux это TCP_CORK — nginx старается упаковать заголовки ответа и начало файла в один TCP-пакет вместо нескольких мелких. Меньше пакетов = меньше overhead.`
### types_hash_max_size 2048; - для чего в конфиге nginx эта строка? - `Тюнинг размера внутренней hash-таблицы, которую nginx строит для быстрого поиска MIME-типа по расширению файла. Трогать почти никогда не нужно, дефолт закрывает 99% случаев.`
### server_tokens off; - для чего в конфиге nginx эта строка? - `Эта директива управляет тем, показывает ли nginx свою версию в заголовке Server: и на стандартных страницах ошибок (404, 500). Если выключено - токены показываются. `
### include /etc/nginx/mime.types; default_type application/octet-stream; - для чего в конфиге nginx эти строки? - `Первое — подключает таблицу соответствий "расширение файла → Content-Type" (.html → text/html, .css → text/css и т.д.). Второе — что отдавать, если расширение не нашлось в таблице: application/octet-stream заставляет браузер скачать файл, а не пытаться его отрендерить как непонятно что.`
### ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3; - для чего в конфиге nginx эти строки? - `Какие версии TLS разрешены для всех HTTPS server block'ов. Тут стоит обратить внимание: TLSv1 и TLSv1.1 официально deprecated (RFC 8996, 2021 год) — их не поддерживают современные security-стандарты (PCI DSS требует минимум 1.2).`
### ssl_prefer_server_ciphers on; - для чего в конфиге nginx эти строки? - `При согласовании шифра сервер навязывает свой порядок предпочтений, а не берёт первый подходящий из списка клиента. Актуально в основном для TLS 1.2 и старее — в TLS 1.3 механизм согласования шифров другой, и эта директива там не так значима.`
### access_log /var/log/nginx/access.log; - для чего в конфиге nginx эти строки? - `Дефолтный access-лог — общий для всех хостов, если конкретный server block не задал свой (у меня eakramar задаёт).`
### gzip on; - для чего в конфиге nginx эти строки? - `Включает сжатие ответов на лету. Остальные gzip_* директивы под ним закомментированы — значит используются встроенные дефолты nginx (gzip_comp_level 1, gzip_types text/html и т.д. — довольно консервативный набор, без application/json, text/css и т.п., которые обычно есть смысл добавить явно).`
### include /etc/nginx/conf.d/*.conf; include /etc/nginx/sites-enabled/*; - для чего в конфиге nginx эти строки? - `Первая строка подхватывает любые .conf-файлы напрямую из conf.d/ (альтернативный паттерн, часто используется на RHEL-подобных системах, на Debian/Ubuntu обычно пустует). Вторая — подхватывает мои server block'ы через симлинки из sites-enabled/, включая eakramar.ru.conf.`
### server { ... } - для чего в конфигурационном файле (server block) nginx эти строки? - `блок описывает один "виртуальный хост". На одном nginx может быть много таких блоков для разных доменов.`
### listen 80; - для чего в конфигурационном файле (server block) nginx эти строки? - `nginx будет принимать соединения на порту 80, это стандартный порт для HTTP (без шифрования). Если позже добавить HTTPS через certbot, появится ещё один блок с listen 443 ssl;.`
### server_name eakramar.ru www.eakramar.ru; - для чего в конфигурационном файле (server block) nginx эти строки? - `говорит nginx: "если в заголовке Host запроса пришёл eakramar.ru или www.eakramar.ru — обслуживай запрос этим блоком". Это то, что позволяет на одном IP держать несколько сайтов (nginx смотрит на Host и выбирает нужный server block).`
### root /var/www/eakramar.ru; - для чего в конфигурационном файле (server block) nginx эти строки? - `корневая директория на диске, откуда nginx будет брать файлы сайта. Запрос на eakramar.ru/about.html физически будет искать файл /var/www/eakramar.ru/about.html.`
### index index.html; - для чего в конфигурационном файле (server block) nginx эти строки? - `если в запросе не указан конкретный файл (например, просто eakramar.ru/), отдавать index.html из root-директории.`
### access_log ... / error_log ... - для чего в конфигурационном файле (server block) nginx эти строки? - `отдельные лог-файлы именно для этого сайта, а не общие /var/log/nginx/access.log. Удобно, когда сайтов несколько — сразу видно, какие запросы/ошибки относятся к какому домену.`
### Что произойдёт если два server block'а слушают один порт с одинаковым server_name? - `Nginx не падает. Это [warn], не [emerg]. nginx -t пройдёт успешно, reload/restart тоже сработают. Nginx оставляет первый по порядку блок как владельца этого имени в таблице для данного порта, а регистрацию второго игнорирует.`
### Что произойдёт если нет ни одного server block с `server_name eakramar.ru`, но запрос пришёл с этим Host заголовком? - `Сработает default_server, обычно первый по порядку.`
### Что такое CA (Certificate Authority)?;`Доверенная третья сторона, которая подписывает сертификаты. Браузер доверяет CA, значит доверяет сертификатам, которые CA выдал.;crypto-https unit-04`
### Что такое X.509 сертификат?;`Стандартный формат цифрового сертификата: содержит публичный ключ, домены (Subject, SAN), срок действия, подпись CA.;crypto-https unit-04`
### Что содержит сертификат?;`Публичный ключ владельца + список доменов (Subject / SAN) + срок действия + подпись CA (доказательство что CA это выпустил).;crypto-https unit-04`
### Что такое приватный ключ и где он хранится?;`Файл на сервере который расшифровывает то, что клиент зашифровал публичным ключом. У Let's Encrypt: /etc/letsencrypt/live/DOMAIN/privkey.pem. Никогда не покидает сервер.;crypto-https unit-04`
### Что такое CSR (Certificate Signing Request)?;`Запрос на подпись сертификата. Содержит публичный ключ + список доменов + подпись приватным ключом. Certbot отправляет CSR в LE — LE возвращает подписанный сертификат.;crypto-https unit-04`
### Видит ли Let's Encrypt мой приватный ключ?;`Нет. Certbot генерирует пару локально, отправляет в LE только CSR (публичный ключ + доказательство владения приватным). Приватный ключ никогда не покидает сервер.;crypto-https unit-04`
### Что такое public key cryptography (асимметричная криптография)?;`Пара ключей: публичный (можно раздать всем) и приватный (только у владельца). Что зашифровано публичным — расшифровать можно только приватным. Что подписано приватным — проверить можно только публичным.;crypto-https unit-04`
### Что такое Root CA?;`Корневой сертификат авторитета. Встроен в ОС и браузеры. Используется редко, приватный ключ в HSM или сейфе. Не выдаёт сертификаты напрямую — подписывает intermediate CA.;crypto-https unit-04`
### Что такое Intermediate CA?;`Промежуточный CA, подписанный root CA. Именно им ежедневно выпускаются миллионы сертификатов. Пример: Let's Encrypt R3, R10, R11.;crypto-https unit-04`
### Что такое Leaf certificate?;`Конечный сертификат — тот что живёт на nginx, для конкретного домена. Подписан intermediate CA. Действителен 90 дней у LE.;crypto-https unit-04`
### Что такое certificate chain / chain of trust?;`Цепочка доверия: leaf сертификат → подписан intermediate CA → подписан root CA. Клиент проверяет всю цепочку до знакомого root (встроенного в ОС).;crypto-https unit-04`
### Что nginx отдаёт клиенту в TLS handshake?;`fullchain.pem = leaf сертификат + intermediate. Root не отдаёт — он уже есть у клиента в trust store ОС/браузера.;crypto-https unit-04`
### Почему root CA не выдаёт сертификаты напрямую?;`Безопасность: root приватный ключ слишком ценный чтобы использовать часто. Хранится оффлайн в HSM. Если утечёт — катастрофа для всей PKI. Поэтому используется через intermediate CA.;crypto-https unit-04`
### Что такое trust store?;`Место в ОС/браузере где хранятся доверенные root CA. Windows: certmgr.msc → Trusted Root. Linux: /etc/ssl/certs/. Браузер доверяет только тем сертификатам, чья цепочка ведёт к root из trust store.;crypto-https unit-04`
### Что такое PKI (Public Key Infrastructure)?;`Инфраструктура открытых ключей: набор ролей (CA, RA), политик и процедур для управления сертификатами. Включает: root CA, intermediate CA, выдачу, отзыв, renewal.;crypto-https unit-04`
### Что такое private CA?;`Собственный корневой CA для внутренней инфраструктуры (домашняя лаба, корпоративная сеть, k8s internal). Работает как публичный CA, но root надо руками установить в trust store клиентов.;crypto-https unit-04`
### Может ли мой self-signed CA работать в интернете?;`Нет. Публично доверенным нужно пройти программы Root Certificate Program (Microsoft, Apple, Mozilla, Google Chrome). Требуются аудиты WebTrust, compliance, годы работы. Private CA работает только для тех, кому вручную установил root.;crypto-https unit-04`
### Что такое Let's Encrypt?;`Некоммерческий Certificate Authority. Бесплатно выдаёт TLS-сертификаты через автоматизированный протокол ACME. Сертификаты действительны 90 дней.;crypto-https unit-04`
### Что такое ACME (Automated Certificate Management Environment)?;`Стандартный протокол (RFC 8555) для автоматического получения сертификатов от CA. Используется Let's Encrypt, ZeroSSL, Google Trust Services и др.;crypto-https unit-04`
### Какие CA поддерживают ACME кроме Let's Encrypt?;`ZeroSSL, Google Trust Services, Buypass. Также private CA как step-ca. Certbot и другие ACME-клиенты работают со всеми ими.;crypto-https unit-04`
### Что такое challenge в ACME?;`Испытание, которое CA даёт клиенту чтобы доказать владение доменом. Два основных типа: HTTP-01 (файл в веб-корне) и DNS-01 (TXT-запись).;crypto-https unit-04`
### Что такое HTTP-01 challenge?;`LE даёт токен, certbot кладёт файл по адресу http://домен/.well-known/acme-challenge/TOKEN, LE делает HTTP GET и проверяет содержимое. Доказывает контроль над веб-сервером.;crypto-https unit-04`
### Что такое DNS-01 challenge?;`Certbot через API DNS-провайдера создаёт TXT-запись _acme-challenge.домен, LE проверяет её через dig. Доказывает контроль над DNS-зоной.;crypto-https unit-04`
### Когда использовать HTTP-01 vs DNS-01?;`HTTP-01: простой публичный сайт, 80 порт открыт, wildcard не нужен. DNS-01: нужен wildcard (*.domain), private инфра без открытого 80 порта, LE не может достучаться к серверу.;crypto-https unit-04`
### Почему HTTP-01 не даёт wildcard-сертификат?;`HTTP-01 доказывает контроль над КОНКРЕТНЫМ именем через файл. Wildcard *.domain покрывает все поддомены — для этого нужно доказать контроль над ВСЕЙ зоной. Это делает только DNS-01.;crypto-https unit-04`
### Что такое key authorization в HTTP-01?;`Строка = токен + "." + JWK thumbprint публичного ключа аккаунта. Именно её certbot кладёт в challenge-файл. Так LE проверяет что запрос идёт от того же аккаунта что зарегистрирован.;crypto-https unit-04`
### Сколько действует сертификат Let's Encrypt?;`90 дней. Философия: короткий срок = меньше окно для злоупотребления скомпрометированным сертификатом + автоматизация renewal.;crypto-https unit-04`
### Когда certbot начинает пытаться обновить сертификат?;`За 30 дней до истечения. Проверяется systemd timer'ом два раза в день. Если срок > 30 дней — ничего не делает.;crypto-https unit-04`
### Что такое staging environment у Let's Encrypt?;`Тестовые серверы LE. Возвращают НЕ-доверенный сертификат (не будет зелёного замка), но без rate limits. Использовать для отладки: certbot --nginx --staging -d domain.;crypto-https unit-04`

### Что происходит при TLS handshake?;`1) ClientHello (клиент → сервер): SNI, поддерживаемые cipher, random. 2) ServerHello (сервер → клиент): выбранный cipher, сертификат, random. 3) Клиент проверяет сертификат. 4) Обмен ключами. 5) ChangeCipherSpec. 6) Дальнейший трафик шифруется session key.;crypto-https unit-04`

### Где в TLS handshake находится SNI?;`В ClientHello — первое сообщение от клиента к серверу. До обмена ключами, до выдачи сертификата. Без SNI сервер не знал бы какой из своих сертификатов отдать.;crypto-https unit-04`

### Что такое ClientHello?;`Первое сообщение TLS handshake. Клиент отправляет: версию TLS, поддерживаемые cipher suites, SNI, random_client (случайные байты), TLS-расширения.;crypto-https unit-04`

### Разница `location /api` vs `location /api/` vs `location ~ ^/api` (три типа матчинга: prefix, exact, regex) `Location — это как nginx решает, куда направить запрос. Reverse proxy без правильной настройки location — это либо всё проксируется через одну дырку, либо ничего не проксируется. Три типа матчинга дают мне гибкость: Точный = — «строго вот сюда»; Префикс — «весь этот раздел URL»; Regex — «всё, что подходит под паттерн». /app — все URL, начинающиеся на «app» (включая /appxyz — обычно плохо); /app/ — все URL под /app/ (обычно правильно для прокси); ~ ^/app — как regex, аналогично префиксу, но с другими правилами обработки. Правильный выбор для reverse proxy — обычно префикс со слешем (location /api/). Он даёт чистые границы, предсказуемое поведение и умеет корректно взаимодействовать с proxy_pass /.`

### gzip_types ...; (nginx) - `Список MIME-типов, которые нужно сжимать. По умолчанию nginx сжимает только text/html — этого мало. Данная настройка охватывает всё обычное текстовое содержимое: text/plain - Обычные текстовые файлы; text/css - Стили CSS; application/json - JSON-ответы API; application/javascript - JavaScript; text/xml, application/xml - XML (RSS-фиды, SOAP-ответы); image/svg+xml - SVG-изображения (они текстовые!). А вот image/png, image/jpeg, video/mp4 — не сжимаются: они уже компрессированы, повторное сжатие бесполезно (даже вредно — процессорное время потратил, а размер тот же или больше). Аналогично application/zip, application/pdf — обычно не сжимают, они уже компрессированные.`
### gzip_min_length 1000; (nginx) - `Не сжимать ответы меньше 1000 байт. Смысл: сжатие само по себе имеет overhead — заголовки алгоритма, служебная информация. Меньше — не трогаем. Можно поставить и меньше (типа 256), если ответы часто на грани. Но 1000 — стандартная рекомендация.`

### add_header. Общий синтаксис (nginx) - `add_header <название> "<значение>" [always];  always — важный флаг. По умолчанию add_header добавляет заголовок только при кодах ответа 200, 201, 204, 206, 301, 302, 303, 304, 307, 308. С флагом always — при любых кодах, включая ошибки (404, 500). Для security-заголовков always обязательно — иначе злоумышленник может атаковать через страницу 404, которая не имеет защитных заголовков.`
### Strict-Transport-Security (HSTS) (nginx) - `Говорит браузеру: «этот сайт только через HTTPS, никакого HTTP, следующие N секунд». Проблема, которую решает:Даже если настроил редирект с HTTP на HTTPS, есть окно для атаки. Пользователь набирает в адресной строке example.com (без https://), браузер идёт по HTTP на порт 80, сервер отправляет редирект 301 → https://example.com.  и в этот первый HTTP-запрос злоумышленник (например, на публичном WiFi) может вклиниться: перехватить запрос, ответить своей поддельной страницей вместо редиректа. Классическая атака SSL Stripping. С HSTS: браузер помнит «этот сайт только HTTPS» — и когда пользователь набирает example.com, браузер сам переписывает URL в https:// до отправки запроса. Никакой уязвимой первой HTTP-попытки. max-age=300 — сколько секунд помнить это правило. 300 секунд = 5 минут. Это очень мало и подходит только для тестирования! В продакшене обычно ставят max-age=31536000 (год) или больше. Логика: раз ты уверен, что HTTPS работает, — держи браузер на короткой цепи. Осторожно с HSTS: если поставить длинный max-age и потом отключить HTTPS — пользователи, у которых заголовок закеширован, не смогут открыть твой сайт до истечения срока. Поэтому в задании 300 секунд — легко откатить. Полные варианты, которые часто добавляют: add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always; includeSubDomains — правило действует и для всех поддоменов, preload — заявка на включение в hardcoded-список браузеров (нужна отдельная регистрация на hstspreload.org)`
### X-Frame-Options. Защита от clickjacking'а (nginx) - `Атака: злоумышленник встраивает твой сайт в <iframe> на своей странице, делает iframe невидимым, и накладывает свои элементы поверх. Пользователь думает, что кликает по «получить подарок», а на самом деле — по «удалить аккаунт» на твоём сайте (пользователь залогинен на твоём сайте). X-Frame-Options: DENY говорит браузеру: не встраивать эту страницу в iframe нигде. Вообще. Варианты значений: DENY — не разрешать встраивание никогда; SAMEORIGIN — разрешить встраивание только со страниц того же домена; ALLOW-FROM uri — старый, уже не поддерживается большинством браузеров. Если сайт не должен встраиваться нигде — DENY самый безопасный вариант. Более современная замена — директива frame-ancestors в Content-Security-Policy, но X-Frame-Options держат для старых браузеров.`
### X-Content-Type-Options. Защита от MIME-sniffing атак (nginx) - `Проблема: браузеры исторически «умные». Если сервер отдаёт файл с MIME-типом text/plain, но содержимое похоже на JavaScript — некоторые браузеры (особенно старый IE) решали «это на самом деле JS, буду исполнять». Это открывало дыру: злоумышленник заливает JavaScript под видом «безобидного» текстового файла (например, аватарка пользователя), а браузер сам решает выполнить его как код. X-Content-Type-Options: nosniff — отключает эту «догадливость». Браузер обязан верить тому MIME-типу, который сервер прислал. Пришёл text/plain — обрабатывать как текст, точка. Значение всегда одно — nosniff. Флаг «включено/выключено». Обязательный заголовок для любого сайта. Никаких минусов.`
### Referrer-Policy (nginx) - `Управляет заголовком Referer, который браузер отправляет при переходе по ссылке. Что такое Referer: когда пользователь на странице https://eakramar.ru/secret-page кликает на ссылку https://google.com, браузер по умолчанию отправляет Google запрос с заголовком: Referer: https://eakramar.ru/secret-page; То есть: «я пришёл со страницы secret-page сайта eakramar.ru». Google теперь знает, откуда пришёл юзер. Проблемы: Утечка информации: путь в URL может содержать чувствительные данные (например, /reset-password?token=xxx); Privacy: посторонние сайты знают, откуда пришёл пользователь. Значение strict-origin-when-cross-origin делает так: На тот же origin (внутри eakramar.ru): отправлять полный URL, без ограничений; На чужой origin (google.com): отправлять только origin (https://eakramar.ru, без пути); С HTTPS на HTTP: не отправлять referrer вообще. Хороший баланс: свои страницы знают, откуда пришли (для аналитики), а чужие получают только «пришёл с eakramar.ru» — без деталей. Другие популярные значения: no-referrer — не отправлять никогда; same-origin — отправлять только внутри своего сайта; strict-origin — только origin, даже своим страницам`
### Content-Security-Policy (CSP) (nginx) - `Самый мощный и самый сложный security-заголовок. Целая мини-политика в одной строке. Что решает: CSP защищает от XSS-атак (Cross-Site Scripting) — самой распространённой веб-уязвимости. XSS — это когда злоумышленник умудряется подсунуть свой JavaScript на страницу твоего сайта, и этот JS выполняется в контексте твоего домена (со всеми правами, включая доступ к куки пользователя). CSP говорит браузеру: «я разрешаю загружать ресурсы только из вот этих источников». Если атакующий смог вставить <script src="http://evil.com/hack.js"></script>— браузер откажется загружать этот скрипт, потому что evil.com не в списке разрешённых. Что означает default-src 'self': default-src — правило по умолчанию для всех типов ресурсов: скриптов, стилей, картинок, шрифтов, XHR-запросов, iframe'ов и т.д. 'self' — разрешить загрузку только с того же origin (тот же протокол, хост, порт — то есть https://eakramar.ru). Проблема: этот минимальный CSP сломает большинство реальных сайтов. Они обычно используют: CDN для jQuery, Bootstrap, Google Fonts, Google Analytics, Inline-скрипты и inline-стили, Изображения с разных источников. Поэтому реальные CSP получаются длинными: add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https:; connect-src 'self' https://api.example.com" always; Каждая *-src директива уточняет правило для своего типа ресурсов. Составить работающий CSP — целое искусство. Есть даже CSP report-only режим для тестирования без блокировки. Для моего простого сайта default-src 'self' может и подойти — если он раздаёт только собственный статический контент. Как проверить: открыть сайт в браузере, F12 → Console. Если видно ошибки типа Refused to load ... — значит CSP слишком строгий, надо расширять.`

- Что произойдёт если два server block'а слушают один порт с одинаковым server_name?

- Что произойдёт если нет ни одного server block с `server_name eakramar.ru`, но запрос пришёл с этим Host заголовком? 
Сработает default_server, обычно первый по порядку.

#### Вывод по командам:
Настройки добавил в конфиг.
1) gzip on; - Включает сжатие для этого server-блока. Без этой строки — nginx ничего не сжимает, даже если указаны другие gzip-директивы.
2) gzip_types ...; - Список MIME-типов, которые нужно сжимать. По умолчанию nginx сжимает только text/html — этого мало. Данная настройка охватывает всё обычное текстовое содержимое: text/plain - Обычные текстовые файлы; text/css - Стили CSS; application/json - JSON-ответы API; application/javascript - JavaScript; text/xml, application/xml - XML (RSS-фиды, SOAP-ответы); image/svg+xml - SVG-изображения (они текстовые!).  SVG сжимается очень хорошо, потому что это XML. А вот image/png, image/jpeg, video/mp4 — не сжимаются: они уже компрессированы, повторное сжатие бесполезно (даже вредно — процессорное время потратил, а размер тот же или больше). Аналогично application/zip, application/pdf — обычно не сжимают, они уже компрессированные.
3) gzip_min_length 1000; - Не сжимать ответы меньше 1000 байт. Смысл: сжатие само по себе имеет overhead — заголовки алгоритма, служебная информация. Для маленьких файлов (условно, ответ в 200 байт) сжатие может дать выигрыш в 20-50 байт или даже увеличить размер. Плюс тратишь CPU на что-то бессмысленное.
Порог 1000 байт — разумная граница. Меньше — не трогаем. Можно поставить и меньше (типа 256), если ответы часто на грани. Но 1000 — стандартная рекомендация.
4) Задание даёт минимум. В продакшене обычно ещё есть: gzip_comp_level 6 - уровень сжатия 1-9 (6 - хороший баланс); gzip_vary on - добавить заголовок "Vary: Accept-Encoding" для кешей; gzip_proxied any - сжимать даже проксированные ответы; gzip_disable "msie6" - старому IE6 не сжимать (у него баги).
5) add_header. Общий синтаксис: add_header <название> "<значение>" [always];  always — важный флаг. По умолчанию add_header добавляет заголовок только при кодах ответа 200, 201, 204, 206, 301, 302, 303, 304, 307, 308. С флагом always — при любых кодах, включая ошибки (404, 500). Для security-заголовков always обязательно — иначе злоумышленник может атаковать через страницу 404, которая не имеет защитных заголовков.
6) Strict-Transport-Security (HSTS). Сокращённо HSTS. Говорит браузеру: «этот сайт только через HTTPS, никакого HTTP, следующие N секунд». Проблема, которую решает:
Даже если настроил редирект с HTTP на HTTPS, есть окно для атаки. Пользователь набирает в адресной строке example.com (без https://), браузер идёт по HTTP на порт 80, сервер отправляет редирект 301 → https://example.com.  и в этот первый HTTP-запрос злоумышленник (например, на публичном WiFi) может вклиниться: перехватить запрос, ответить своей поддельной страницей вместо редиректа. Классическая атака SSL Stripping. С HSTS: браузер помнит «этот сайт только HTTPS» — и когда пользователь набирает example.com, браузер сам переписывает URL в https:// до отправки запроса. Никакой уязвимой первой HTTP-попытки. max-age=300 — сколько секунд помнить это правило. 300 секунд = 5 минут. Это очень мало и подходит только для тестирования! В продакшене обычно ставят max-age=31536000 (год) или больше. Логика: раз ты уверен, что HTTPS работает, — держи браузер на короткой цепи. Осторожно с HSTS: если поставить длинный max-age и потом отключить HTTPS — пользователи, у которых заголовок закеширован, не смогут открыть твой сайт до истечения срока. Поэтому в задании 300 секунд — легко откатить. Полные варианты, которые часто добавляют: add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always; includeSubDomains — правило действует и для всех поддоменов, preload — заявка на включение в hardcoded-список браузеров (нужна отдельная регистрация на hstspreload.org)
7) X-Frame-Options. Защита от clickjacking'а. Атака: злоумышленник встраивает твой сайт в <iframe> на своей странице, делает iframe невидимым, и накладывает свои элементы поверх. Пользователь думает, что кликает по «получить подарок», а на самом деле — по «удалить аккаунт» на твоём сайте (пользователь залогинен на твоём сайте).
X-Frame-Options: DENY говорит браузеру: не встраивать эту страницу в iframe нигде. Вообще. Варианты значений: DENY — не разрешать встраивание никогда; SAMEORIGIN — разрешить встраивание только со страниц того же домена; ALLOW-FROM uri — старый, уже не поддерживается большинством браузеров. Если сайт не должен встраиваться нигде — DENY самый безопасный вариант. Более современная замена — директива frame-ancestors в Content-Security-Policy, но X-Frame-Options держат для старых браузеров.
8) X-Content-Type-Options. Защита от MIME-sniffing атак. Проблема: браузеры исторически «умные». Если сервер отдаёт файл с MIME-типом text/plain, но содержимое похоже на JavaScript — некоторые браузеры (особенно старый IE) решали «это на самом деле JS, буду исполнять». Это открывало дыру: злоумышленник заливает JavaScript под видом «безобидного» текстового файла (например, аватарка пользователя), а браузер сам решает выполнить его как код. X-Content-Type-Options: nosniff — отключает эту «догадливость». Браузер обязан верить тому MIME-типу, который сервер прислал. Пришёл text/plain — обрабатывать как текст, точка. Значение всегда одно — nosniff. Флаг «включено/выключено». Обязательный заголовок для любого сайта. Никаких минусов.
9) Referrer-Policy. Управляет заголовком Referer, который браузер отправляет при переходе по ссылке. Что такое Referer: когда пользователь на странице https://eakramar.ru/secret-page кликает на ссылку https://google.com, браузер по умолчанию отправляет Google запрос с заголовком: Referer: https://eakramar.ru/secret-page; То есть: «я пришёл со страницы secret-page сайта eakramar.ru». Google теперь знает, откуда пришёл юзер. Проблемы: Утечка информации: путь в URL может содержать чувствительные данные (например, /reset-password?token=xxx); Privacy: посторонние сайты знают, откуда пришёл пользователь. Значение strict-origin-when-cross-origin делает так: На тот же origin (внутри eakramar.ru): отправлять полный URL, без ограничений; На чужой origin (google.com): отправлять только origin (https://eakramar.ru, без пути); С HTTPS на HTTP: не отправлять referrer вообще. Хороший баланс: свои страницы знают, откуда пришли (для аналитики), а чужие получают только «пришёл с eakramar.ru» — без деталей.
Другие популярные значения: no-referrer — не отправлять никогда; same-origin — отправлять только внутри своего сайта; strict-origin — только origin, даже своим страницам
10) Content-Security-Policy (CSP). Самый мощный и самый сложный security-заголовок. Целая мини-политика в одной строке. Что решает: CSP защищает от XSS-атак (Cross-Site Scripting) — самой распространённой веб-уязвимости. XSS — это когда злоумышленник умудряется подсунуть свой JavaScript на страницу твоего сайта, и этот JS выполняется в контексте твоего домена (со всеми правами, включая доступ к куки пользователя). CSP говорит браузеру: «я разрешаю загружать ресурсы только из вот этих источников». Если атакующий смог вставить <script src="http://evil.com/hack.js"></script>— браузер откажется загружать этот скрипт, потому что evil.com не в списке разрешённых. Что означает default-src 'self': default-src — правило по умолчанию для всех типов ресурсов: скриптов, стилей, картинок, шрифтов, XHR-запросов, iframe'ов и т.д. 'self' — разрешить загрузку только с того же origin (тот же протокол, хост, порт — то есть https://eakramar.ru). В результате:
✅ <script src="/js/app.js"> — свой, разрешено
✅ <img src="https://eakramar.ru/logo.png"> — свой, разрешено
❌ <script src="https://cdn.example.com/lib.js"> — чужой CDN, запрещено
❌ <img src="http://evil.com/hack.png"> — совсем чужое, запрещено
❌ <script>evil_code()</script> — inline-скрипты запрещены (это важная защита!)
Проблема: этот минимальный CSP сломает большинство реальных сайтов. Они обычно используют: CDN для jQuery, Bootstrap, Google Fonts, Google Analytics, Inline-скрипты и inline-стили, Изображения с разных источников. Поэтому реальные CSP получаются длинными: add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https:; connect-src 'self' https://api.example.com" always; Каждая *-src директива уточняет правило для своего типа ресурсов. Составить работающий CSP — целое искусство. Есть даже CSP report-only режим для тестирования без блокировки. Для моего простого сайта default-src 'self' может и подойти — если он раздаёт только собственный статический контент. Как проверить: открыть сайт в браузере, F12 → Console. Если видно ошибки типа Refused to load ... — значит CSP слишком строгий, надо расширять.

#### Что я понял:
Gzip-часть — про производительность: сжимаем текстовые ответы, экономим трафик, ускоряем загрузку. Простая настройка, огромный эффект. Никаких минусов кроме крохотной нагрузки на CPU.
Security headers — про безопасность: браузер делает больше проверок и запретов, защищая пользователя. Разные заголовки — от разных классов атак.
Заголовок                             От чего защищает
Strict-Transport-Security             SSL stripping, downgrade-атаки
X-Frame-Options                       Clickjacking через iframe
X-Content-Type-Options                MIME-sniffing атаки
Referrer-Policy                       Утечка информации через Referer
Content-Security-Policy               XSS (главная угроза веб-приложений)
Все они работают в связке с браузером: сервер декларирует правила, браузер их применяет. Это defence in depth — многослойная защита. Даже если в приложении баг с XSS, CSP может не позволить атаке сработать. Флаг always для всех security-заголовков — чтобы они попадали и в ответы с ошибками, не только в 200-е. max-age=300 для HSTS — это тестовый минимум. В продакшене — год или больше, но только когда уверен, что HTTPS точно останется навсегда. Оба блока — очень практичная база для любого веб-сервера. Не «security theater», а реальные защиты, которые ловят большинство типовых атак.

### **Что записать в раздел "Ключевые выводы для дежурства":**
- **Не переопределения**, а **действия** в стиле "если Х — сделай Y":
  - "Сайт не открывается → в первую очередь `nginx -t` + `journalctl -u nginx -n 50`"
  - "502 Bad Gateway → backend упал, проверь `ss -tlnp | grep :PORT` — слушает ли твой upstream"
  - "504 Gateway Timeout → backend жив но тормозит, крути `proxy_read_timeout`"
  - "Сертификат — проверь дату: `openssl x509 -in /path -noout -dates`"
  - "После правки конфига **всегда** `nginx -t` перед `reload`"
