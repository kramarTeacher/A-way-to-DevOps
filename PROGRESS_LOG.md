2. ufw vs iptables vs nftables — что под капотом, что выбрать в 2026?
Это три слоя, лежащих друг на друге. Внизу — реализация в ядре, сверху — удобные обёртки. 1. Простые пользовательские обертки: ufw, firewalld. 2. Нативные CLI-инструменты: iptables, nft. 3. Реализация в ядре: nf_tables (kernel subsystem). Все дороги ведут в ядро — в подсистему nf_tables. Она одна и делает работу. А верхние слои — просто разные способы её настроить. nf_tables — это подсистема ядра Linux, отвечающая за фильтрацию сетевого трафика, NAT, mangling. Введена в ядро в 2014 году, с тех пор постепенно вытесняет старую iptables-подсистему. Это код внутри ядра, который принимает решения о пакетах. С ним общаются через специальные системные вызовы (netlink). iptables — это утилита командной строки, появившаяся в 1998 году. Она работала со старой подсистемой ядра x_tables (та, что была до nf_tables), сам инструмент iptables остался, но переехал на новую подсистему nf_tables. То есть команды те же, синтаксис привычный, а под капотом — уже новая ядерная реализация. Это называется iptables-nft — совместимая обёртка. nft — это родная утилита для nf_tables. Свой синтаксис, свои возможности, более современная логика. UFW (Uncomplicated Firewall) — «файрвол для людей». Разработан в Ubuntu, оттуда и распространился. Синтаксис максимально простой, под капотом UFW генерирует правила для nftables (или iptables на старых системах) и применяет их. Нне думаешь про цепочки, hook priorities, families — это делает UFW. Что использовать в 2026 году:
Простой сервер, домашний use case, «прикрыть порты и не думать» - UFW;
Production-сервер, кастомная сеть, интересные задачи - nft;
Легаси-скрипты, старые туториалы, чужой готовый код - iptables (iptables-nft);
Kubernetes, контейнеры, продвинутые сетевые фильтры - nftables + сетевые CNI-плагины (Cilium, Calico), возможно, eBPF;
Enterprise, RHEL/CentOS/Rocky/Alma - firewalld.

4. SSH bastion / jump host — зачем нужен, нарисуй схему словами (клиент → bastion → внутренний сервер)
SSH Bastion (другое название — Jump Host) — это специальный защищённый сервер, который работает как единственная «входная дверь» в закрытую сеть. Он нужен для двух главных целей: Безопасность: не выставляются во внешний интернет (Интернет) свои рабочие серверы с базами данных или приложениями. В сети виден только один сервер — бастион, который максимально укреплён (минимальный набор ПО, строгие ключи, логирование). Управление доступом: Через бастион проходит авторизация один раз, а дальше он пускает только к тем внутренним серверам, к которым есть доступ (работает как шлюз). [ (Клиент) ]Стучится в главные ворота. Соединение → ВНЕШНЯЯ СЕТЬ (Интернет) (Трафик идет по защищенному протоколу SSH на единственный публичный IP-адрес). [ SSH BASTION (Шлюз) ](Стоит на границе сети, имеет белый (публичный) IP-адрес. У него жесткая защита, он слушает только 22-й порт). Бастион проверяет SSH-ключ и спрашивает: «Куда вы собираетесь?». Внутреннее соединение (SSH-туннель) (Бастион не передает ваш компьютер внутрь, а сам устанавливает НОВОЕ защищенное соединение от своего имени во внутреннюю сеть). [ ВНУТРЕННИЙ ЦЕЛЕВОЙ СЕРВЕР ]
5. Назови 5 обязательных правил hardening Ubuntu-сервера с обоснованием каждого.
5.1. Non-root user + sudo: создать пользователя, добавить в группу sudo, отключить root SSH
Цель: снизить уровень угрозы получения корневых прав для несанкционированных пользователей, контроль действий каждого сотрудника.
5.2. SSH ключи вместо паролей (PasswordAuthentication no, PubkeyAuthentication yes)
Усиливает безопасность и снижает вероятность взлома с помощью брутфорса.
5.3. Файрвол (UFW или nftables) — закрыть всё, кроме нужного
Создает политику, которая сильно защищает систему от атак, выключает не нужные порты, настраивает политику приема и передачи информации.
5.4. Автоматические обновления безопасности (unattended-upgrades)
Необходимо для защиты от уязвимостей, например, обнаружили уязвимость в ядре, через которую злоумышленики могут навредить системе, далее команда ubuntu выпускает патч, а моя система скачивает и устанавливает этот патч, при чем может без меня. И дальше уже эта уязвимость не сработает.
5.5. Fail2ban — защита от брутфорса
Защищает от ssh брутфорса, 5 неверных попыток и бан.
6. **Новый:** зачем в firewall правило `ct state established,related accept`?

### Ответы на тест
1. 4 причины использовать reverse proxy.
1.1. Экономия. На одном ip можно размещать несколько ресурсов, прокси сама будет решать какому ресурсу передавать запрос, вывод: экономия ip адресов - экономия денег;
1.2. Безопасность + простота. Настройки безопасности производятся на узле прокси, вывод: не надо захламлять бэкенд настройками безопасности;
1.3. Логирование. Прокси может собирать логи о доступе и о ошибках в одном месте - у себя, вывод: единая точка аккумуляции информации о входе и ошибках - это хорошо.
1.4. Анонимность. Клиент, делающий запрос, не видит где в моей архитектуре располагается сервер, это знает только прокси, вывод: такая схема создает неизвестность как для обычных клиентов, так и для злоумышленников, это хорошо.
1.5. Балансировка нагрузки. Один сайт крутится на 10 серверах, Nginx распределяет запросы, вывод: такая схема позволяет разгрузить каналы и дать быстрее требуемый контент;
1.6. Простота управления. Сертификат стоит только на прокси, внутренние сервера работают без TLS, вывод: проще администрировать;
1.7. Кэширование статики. Картинки и CSS отдаёт прокси, не грузя бекенд, вывод: понижение нагрузки на бэкенд;
1.8. WAF. Фильтрация вредоносных запросов до того как они дойдут до приложения.
2. Что делает HSTS? Риск большого max-age?
HSTS - (Strict-Transport-Security) это один из заголовков безопасности, он позволяет сделать такую настройку, которая даст инструкцию для браузера - использовать https для указанного ресурса. Нюанс, связанный с большим max-age связан с тем, что инструкция уже разослана в браузеры и живёт там независимо от меня. Если сломается сертификат — вернуть пользователей на HTTP до истечения max-age нельзя, поэтому для теста и отладки лучше ставить 5 минут.
3. `proxy_pass http://localhost:3000` vs `proxy_pass http://localhost:3000/` (со слешом).
3.1. Без слеша не будет делать обрезку url при матчинге, то есть, если клиент шлет запрос: https://eakramar.ru/app/, получая его, nginx не делая обрезку, перешлет приложению GET /app/, в результате приложение даст ошибку, так как, не обрабатывает данную диреткорию;
3.2. Со слешем будет делать обрезку url при матчинге, то есть, если клиент шлет запрос: https://eakramar.ru/app/, получая его, nginx делая обрезку, перешлет приложению GET /, в результате приложение сможет корректно обработать запрос.
4. Как настроить автообновление LE-сертификата, чтобы не забылось?
В ходе выполнения эксперимента, я понял, что эта процедура выполняется на автомате, для этого нужно: 1. установить certbot - apt install certbot python3-certbot-nginx -y; 2. Получить сертификат для своих доменов - certbot --nginx -d eakramar.ru -d www.eakramar.ru; 3. Можно проверить путем эмулированния автообновления - certbot renew --dry-run. При установке certbot создается сервис и таймер для certbot, таймер запускает сервис, который смотрит на срок сертификата и перевыпускает, если срок 30 или меньше суток.
5. Сайт работает по HTTP, на HTTPS — connection refused. Что проверять?
Если чисто на в скидку, ситуация говорит о том, что бэкенд рабочий, иначе бы и по http не зашло. Здесь скорее всего проблема в настройках https, тогда лучше смотреть nginx.conf и конфиг сервер блока. Ты мне давал чек лист из 6 пунктов, я бы для диагностики применил его, но со следующим порядком:

### Мои ответы на тест по юниту

1. 10 шагов, что происходит между вводом `https://google.com` и получением ответа.
1.1. Браузер смотрит в свой DNS-кэш, если не находит запись, то обращается к DNS-резолверу хоста.
1.2. Хост ищет в своем DNS-кэш запись, если не находит, то делает рекурсию запрос.
1.3. После того как хост получит запись DNS, он передает информацию приложению.
1.4. На канальном уровне, честно скажу не знаю, что будет происходить, но скорее всего в кадре будет указан MAC-источник - это сам хост с браузером, MAC-получателя - это шлюз на следующем хопе или интерфейс на границе сети и по-моему еще указывается протокол сетевого уровня.
1.5. На сетевом уровне трафик будет маршрутизироваться пока не достигнет точки назначения, по адресу, который зарезолвил.
1.6. На транспортном уровне по протоколу TCP будет формироваться соединение с сервером, которое начинается с тройного рукопожатия.
1.7. Клиент при этом отправляет пакет с флагом SYN (например, seq=1000).
1.8. Сервер в ответ направит пакет с флагом SYN-ACK (например, seq=5000, ack=1001).
1.9. В ответ клиент пришлет пакет с флагом ACK (например, ACK=5001) и после этого соединение будет считаться установленным на уровне TCP и дальше могут передаваться данные.
1.10. По скольку на прикладном уровне был задействован протокол https, то должно установиться TLS-соединение. TLS-соединение устанавливается на прикладном, если брать за основу архитектуру стека TCP/IP (если взять за основу теоретическую концепцию модели OSI, то это будет происходить на уровне представления).
1.11. При установке TLS-соединения клиент шлет пакет ClientHello, в котором указывает доступные ему версии TLS, шифры, которые он знает, а еще рандомное число.
1.12. Сервер в ответ шлет пакет со своим рандомным числом, выбранные шифры и версии TLS.
1.13. Сервер шлет свой публичный ключ, сертификат, подпись CA.
1.14. Клиент начинает проверять сертификат, после шлет пакет ClientKeyExchange, в котором будет шифр pre-master secret зашифрованный публичным ключем, рандомными числами клиента и сервера.
1.15. На следующем этапе уже нельзя ничего прочитать, если отлавливать пакеты на интерфейсе. Клиент шлет пакет ChangeCipherSpec + Finished теперь все шифруется, вот только не помню шифруется с помощью pre-master secret или на основе pre-master secret и рандомных чисел создается новый session key.
1.16. Сервер шлет пакет ChangeCipherSpec, в котором подтверждает готовность. Теперь зашифрованный канал данных создан и начинается передача данных со страницы https://google.com

2. CNAME vs A. Когда CNAME использовать **нельзя**?
A-запись хранит информацию о переводе доменного имени в IP-адрес.
CNAME записит хранит алиас, можно назвать псевдонимом, например, если на сервере можно создать запись, которая будет редиректить запросы eakramar.ru на mx.eakramar.ru
Нельзя создать CNAME для самого домена (например, eakramar.ru)
3. Команда: какие name-серверы у `example.com`?
dig example.com NS
4. Домен резолвится по dig, но в браузере — нет. 4 причины.
4.1. Жесткий кэш DNS в самом браузере.
4.2. Проблема с SNI или прокси/DoH (DNS-over-HTTPS).
4.3. Браузер пытается открыть HTTPS, а сервер слушает только HTTP (или наоборот)
4.4. Прокси-сервер или файл hosts (нестандартная маршрутизация).
5. Команда: все TCP-соединения с PID, без DNS-резолвинга.
ss -tnp
