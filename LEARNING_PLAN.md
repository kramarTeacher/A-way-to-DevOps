## Стратегия "мозг свежий vs мозг устал"

Главный принцип эффективности при твоём графике.

### На свежую голову (утро межвахты, выходные, отпуск)

- Изучение **новых концепций**
- Практические эксперименты, написание кода
- Чтение книг
- Создание Anki-карточек по новому материалу

### Когда устал (вечер после стройки, конец недели межвахты)

- Просмотр своих заметок
- Лёгкие YouTube-разборы по уже знакомому
- Anki — повторение

### На вахте (после 12-часовой смены)

- **Только Anki** — 10-20 минут, когда есть окно
- Иногда — перечитывание заметок с прошлой межвахты
- **Никаких** новых тем, новых книг, нового кода
- Цель вахты — не забыть пройденное, а не узнать новое

### Anki как multiplier

Если на каждой межвахте **создаёшь** карточки по пройденному, а на вахте **повторяешь** их — на следующей межвахте не тратишь время на "вспомнить, что было". Сразу идёшь дальше. Это даёт реальный +20% к усвоению при том же количестве часов.

### Тест юнита 2

1. systemd timer vs cron — минимум 3 различия.
2. Команда: логи nginx за последний час, только error-уровень.
3. `Restart=on-failure` vs `Restart=always` — разница.
4. Как сделать, чтобы сервис стартовал после network и БД?

<details><summary>Эталонные ответы</summary>

1. (а) timer пишет в journald, cron шлёт письма; (б) timer поддерживает зависимости от unit'ов; (в) `Persistent=true` запустит пропущенное после downtime; (г) точность таймера до миллисекунд.
2. `journalctl -u nginx --since "1 hour ago" -p err`. Уровни: emerg(0)…debug(7).
3. `on-failure` — рестарт только при ненулевом exit или kill. `always` — при любом завершении (включая `systemctl stop`).
4. `[Unit]` секция: `After=network-online.target postgresql.service` + `Wants=network-online.target` (или `Requires=postgresql.service`).
5. `journalctl -u cron`, `/var/log/syslog`. Типичные баги: минимальный PATH, CWD=`/`, нет переменных окружения.

</details>

### Эксперимент 3 🧠 — tcpdump: захват HTTP и DNS трафика

**Что делаем:** увидеть **что реально летает по сети**, а не только что показывает браузер.

**Подготовка:**
```bash
sudo apt install tcpdump  # если ещё нет
```

**Сценарий А — DNS запросы:**
```bash
# Терминал 1 — захват DNS трафика (порт 53)
sudo tcpdump -i any -n port 53 -A

# Терминал 2 — генерируем DNS запрос
dig eakramar.ru
nslookup google.com
```

**Сценарий Б — HTTP трафик:**
```bash
# Терминал 1 — захват HTTP (порт 80)
sudo tcpdump -i any -n port 80 -A -s 0

# Терминал 2 — простой HTTP запрос
curl http://neverssl.com
# (neverssl.com специально не редиректит на HTTPS, удобно для эксперимента)
```

**Сценарий В — HTTPS (увидишь handshake, но не контент):**
```bash
# Терминал 1
sudo tcpdump -i any -n port 443 -A -s 0 | head -100

# Терминал 2
curl https://google.com
```

**Что записать:**
- В DNS-трафике видишь имена доменов в открытом виде? (да, DNS без DoH/DoT — plaintext)
- В HTTP видишь содержимое страницы? (да)
- В HTTPS видишь что-то осмысленное? (нет, после handshake — шифр)
- Что такое SYN, SYN-ACK, ACK в выводе tcpdump? (это TCP 3-way handshake)

**Полезные флаги tcpdump:**
- `-i any` — слушать все интерфейсы
- `-n` — не резолвить имена (быстрее, чище вывод)
- `-A` — печатать payload в ASCII
- `-s 0` — захватывать пакет целиком (без обрезки)
- `-c 10` — захватить только 10 пакетов и выйти
- `-w file.pcap` — сохранить в файл (потом можно открыть в Wireshark)

**Вопросы:**
- Сколько пакетов летит в `dig eakramar.ru`? (обычно 2: запрос + ответ)
- Что такое UDP в DNS-выводе? Почему DNS на UDP, а не TCP?
- Когда DNS использует TCP вместо UDP? (Подсказка: ответ >512 байт, или AXFR — зонный трансфер)

### Эксперимент 4 📺 — traceroute vs mtr: путь пакета

**Что делаем:** увидеть путь сетевого пакета через интернет.

**Команды:**
```bash
# Установка mtr если нет
sudo apt install mtr-tiny

# Классический traceroute
traceroute google.com
traceroute -I google.com  # ICMP (как ping) вместо UDP

# mtr — то же, но в реальном времени с потерями пакетов
mtr google.com           # интерактивный режим, выйти q
mtr -r -c 10 google.com  # один отчёт за 10 циклов

# Полезно для диагностики — проверь несколько целей
mtr -r -c 5 1.1.1.1      # Cloudflare DNS
mtr -r -c 5 8.8.8.8      # Google DNS
mtr -r -c 5 eakramar.ru  # твой домен через CF
```

**Что записать:**

### Тест юнита 11

1. Что делает SPF, как проверяется получателем?
2. DKIM vs SPF — принципиальная разница, что вместе закрывают?
3. Cloudflare proxied — плюсы и минусы.
4. A-запись 1.2.3.4, в CF proxied. Что покажет `dig` и почему?
5. DMARC `p=quarantine` vs `p=reject` — когда что?

<details><summary>Эталонные ответы</summary>

1. SPF — TXT-запись с разрешёнными отправителями. Получатель смотрит Return-Path → SPF домена → проверяет IP в списке.
2. SPF — **откуда** (IP). DKIM — **что контент не изменён**, подписан приватным ключом домена. Вместе: имеет право отправлять + контент не подделан. DMARC объединяет.
3. Плюсы: DDoS, кэш, WAF, скрытие реального IP. Минусы: CF видит весь HTTPS-трафик; не-HTTP порты ломаются.
4. Покажет **IP Cloudflare**. В proxied A-запись подменяется anycast-IP CF.
5. `quarantine` — в спам. `reject` — отклонить. Стратегия: `p=none` → `p=quarantine pct=10` → `p=reject`.

</details>
